## Re-sync risks
- CSS is scraped from the storybook build ([CSS_FROM_STORYBOOK]): it is a Tailwind *subset* (only classes used by stories/components) and it also carries storybook-only globals (`html,body{font-family:var(--font-sans)}` with Inter, `body{background-color:var(--background)}`, `--cursor-interactive: pointer`). Designs inherit those. If storybook's globals.css changes, designs change. The conventions header lists verified classes - re-run its validation after each sync (`grid-cols-2`, `px-6`, `md:` variants are deliberately documented as NOT available).
- Inter is a remote Google Fonts @import ([FONT_REMOTE]) - requires network at render time.
- Three lib forks in .design-sync/overrides/ (preview-gen-storybook, docs, source-storybook) are copies of the skill's lib modules at skill v2.1.308 with small [FORK] edits; after a skill update, diff them against the new .ds-sync/lib versions and re-apply the [FORK] blocks.
- Six stories skipped for a compare-harness false positive (FocusScope sentinel, each probe-verified to render): ColorSwatchPicker Default + Disabled + With Default Value + With Custom Indicator (all whose root starts with the FocusScope span; Extended Palette wraps it in a div and captures fine), ListBox Default + Virtualization.
- ScrollShadow Orientation + Visibility Change skipped: both contain a HORIZONTAL ScrollShadow and wedge the chromium renderer during compare's element screenshot (`animations: 'disabled'`) - the 8s screenshot timeout never fires and the whole capture browser hangs at 100% CPU. This is what stalled two fan-out batches. Both stories render fine in storybook normally (probe-verified); only the screenshot step hangs. Horizontal API is still documented in ScrollShadow.prompt.md. If a future capture hangs, first suspect a story with horizontal ScrollShadow.
- [STORY_CAP]: compare grades only the first 6 stories per component; many components have 10-26 stories (Calendar 26, Autocomplete 21, InputGroup 20). Tail stories were never captured.
- Overlay stories (Modal, AlertDialog, Drawer, Popover, Tooltip, Toast, Dropdown, pickers) capture closed on both sides - open overlay surfaces are not pixel-verified.
- Built with Node 24.22.1, pnpm 10.26.2 (corepack), Storybook 10.6.0, @heroui/react 3.2.6.
- Story previews that use `@iconify/react` (Accordion, Card, Alert, ...) fetch icon data from the Iconify API at runtime on BOTH panels; a capture can fire before icons arrive (seen once on Accordion Default storybook side; recapture fixed it). Missing iconify icons on one side = recapture first. Note: iconify is story-only - it is not in the HeroUI bundle, so the design agent cannot use it (conventions.md points to the bundled Icon* exports / inline SVG).
- [GENERAL] Under 4-way concurrent capture, a compare run once reported a whole component `unpaired`/"(no shot)" (Badge) despite a valid wrapper; a solo re-run captured cleanly. Re-run solo before diagnosing an unpaired with a valid wrapper.
- Toolbar graded `close` on Vertical / With Button Group / Attached: the story places `ButtonGroup.Separator` (position:absolute) directly in a ButtonGroup with no positioned ancestor. Storybook renders it off-canvas (x=-1); the preview cell is position:relative, so a stray 1px line shows at the cell edge. Toolbar rendering itself is identical. Fix belongs upstream in the story (or wrap groups in a positioned element); not worked around in an owned preview.
